fix: /loop REFUSES a contract flag instead of silently dropping it

`/loop` has no finish line, so every contract clause is meaningless to it — and
they were built and then dropped by an `isGoal ? ... : {}` spread:

  /loop "audit" severity=high preAuth=1     → a loop starts, both flags ignored,
                                              nothing says so

Someone who typed that reasonably concluded the run was scoped. It was not.

Refused, not warned: a warning still starts the loop with the flags ignored, which
is the failure it is warning about. Nothing is started, and the message names
exactly which flags it rejected and the two ways forward:

  REJECTED: /loop does not take contract flags, and these would have been silently
  ignored: severity, preAuth.

  A /loop has no finish line, so there is nothing for a contract clause to gate.
  NOTHING WAS STARTED.

    want a finish line ("one high finding and stop")?
        /goal "<objective>" severity=<value> preAuth=<value>

    want to SCOPE a loop instead?
        /loop "<objective>" focus=<class>,<class>

  category= is a contract FILTER — only findings in those classes count.
  focus= is a PREFERENCE — generation and scheduling favour those classes, and
  other classes are still recorded, because a pre-auth RCE is often reached by
  chaining a finding from somewhere else.

AND THE BUG FOUND WHILE DOING IT: THREE DOCUMENTED FLAGS NEVER WORKED.

The usage line advertises `reproduced=1`, `impact=1` and `preAuth=1`. The parser
only ever read `requireReproduced`, `requireImpact` and `requirePreAuth`. So on a
/goal, three flags printed in the help did nothing at all — the same silent ignore
this commit refuses for /loop.

Both spellings are accepted now, and the refusal recognises both.

- The usage line for /loop no longer advertises contract flags.
- The refusal names what you TYPED, not a canonical spelling.
