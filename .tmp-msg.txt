feat: /loopsec can combine findings — a chain is a finding

The operator's question was whether the model combines findings as rounds accumulate.
It could not. `sec.ts` mentioned chain/combine/requires EXACTLY TWICE, and both were
comments explaining what was ABSENT — the report had no combination section and
`renderFoundSoFar` handed over a flat list with no hint that F-0001 and F-0007 might be
one bug.

That was a design mistake, not a trade. COMBINATION IS ORTHOGONAL TO THE ASSERTION GATE:
the gate is what this mode drops, and chaining was never about assertions. It got
dropped along with them.

WHY IT MATTERS

    an arbitrary file write                     → medium
    that write into a file that gets executed   → root RCE

Two findings, one bug. A report that lists them separately and never says the word has
missed the finding — and that is exactly what this mode did.

WHAT WAS ADDED

- `SecFinding.chainOf?: string[]` — two or more existing finding ids. A chain needs NO
  artifact of its own: its artifact IS its parts, each of which already carries one.
  Demanding a third would push the model to attach something unrelated just to pass the
  check, which is worse than the check is worth. Every id must already exist, and the
  refusal NAMES the findings it does have so the next call can be right.
- The analyze brief asks the combination question on every round, and only once there is
  something to combine — modelled on the hypothesis mode's pursue question 4.
- `FOUND SO FAR` marks what is already chained (`⛓ combines F-0001 + F-0002`) and lists
  the chains separately, because a model that cannot see the relationships cannot build
  on them.
- The report gets a `## 组合链` section BEFORE the findings, a summary row, and a
  per-finding `**组合自：**` label so a reader who scrolls the flat list still sees it.
- `sec_finding` gains `chainOf`, and its guidelines now say to ask the question every time.

A BUG THE TESTS CAUGHT, AND IT IS THE FIFTH OF ITS KIND

I updated the WRITE-side gate (`validateFinding`) and not the READ-side one
(`normalizeFinding`), so `recordFinding` returned ok and the finding was not in the
snapshot — accepted on the way in, dropped on the way back out, with no error anywhere
because the record that lost it still validated. It is the same shape as the allowlist
bug that has now eaten four fields in this file, and it is why the requirement is stated
in two places and has to be stated in both.

VERIFICATION

11 new tests: the artifact exemption, the chain-of-one refusal, the unknown-id refusal
naming what exists, the repeated-id refusal, the store round trip, the brief asking the
question (and NOT asking it before there is anything to combine), FOUND SO FAR marking
chains, the report's section ordering, and a run with no chains showing no section at
all. Driven end to end: two medium findings combined into one critical, printed as
`F-0003 [严重]` with its parts named.

823 tests, 0 failures, tsc clean.
