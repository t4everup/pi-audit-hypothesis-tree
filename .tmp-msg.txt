fix: `focus=` never reached the GENERATE brief — the only place it could save work

Measured on a real /loop run (loop_Avocent_DSView4, 31 hypotheses, 14 rounds, 31
minutes):

  by kind        rounds  median gap   total time
  generate            7        55s      12.2 min   44%
  recon               2       266s       7.9 min   28%
  consolidate         2       170s       3.9 min   14%
  verify              2       150s       3.9 min   14%

  categories: {auth-bypass: 19, info-disclosure: 4, csrf: 3, sqli: 3, xxe: 1, deserialization: 1}

61% of the tree was auth-bypass, and the run had no focus= — so ~19 of 31 future
verify rounds (at ~150s each, ~47 minutes) would go to a class the goal did not
name.

AND THEN THE BUG. The focus line was pushed inside `renderRoundBrief` AFTER the five
early returns:

  if (kind === "coverage")  return …     ← focus never added
  if (kind === "recon")     return …     ← focus never added
  if (kind === "generate")  return …     ← focus never added   ← THE ONE THAT MATTERS
  if (kind === "challenge") return …     ← focus never added
  if (kind === "pursue")    return …     ← focus never added
  … then push the focus                  ← only verify/combine got it

So `focus=` reached the ONE brief where it can only REORDER work, and never the one
where it can REDUCE it. The scheduler bias worked; the instruction did not.

- The focus is now added by `withBriefExtras`, the composer that already wraps every
  brief, so no early return can bypass it.
- `afterBanner()` is extracted and shared with the operator notes, which had the
  same insert-after-the-banner logic inline.
- The test that was supposed to catch this only exercised a VERIFY round — the one
  brief that had it. It now walks a full loop and asserts the focus is in EVERY kind
  of brief it saw, and that `generate` was among them.

733 tests, 0 failures.
