fix: a tree full of BLOCKED nodes cycled forever instead of stopping

Reported as a question: "if I ask it to find pre-auth RCE, will the loop get stuck
on the authentication part building hypotheses, doing a lot with no results and
never switching direction?"

THE SCHEDULER DOES NOT TUNNEL — measured on the real Centreon pick history:

  category mix over 29 picks: auth-bypass 8, info-disclosure 6, command-injection 5,
    privilege-escalation 2, sqli 2, other 2, idor 1, deserialization 1, rce 1,
    open-redirect 1
  longest run of the SAME category: 2 picks
  auth-bypass share: 28% (the cap is 40%)

Ten categories, never three in a row. MAX_CATEGORY_RATIO works.

BUT THE FEAR WAS RIGHT, BY A DIFFERENT ROUTE. `isSchedulable` uses `isOpen`, and
`isOpen("blocked")` is TRUE — blocked is not a verdict — so a blocked node stays a
scheduling candidate. Combined with the recent change that counts `blocked` as
progress (an honest "I cannot settle this from the source" IS an examination),
that produced exactly the reported failure:

  model blocks a node -> still schedulable -> picked again -> blocked again ->
  every round counts as productive -> the plateau can NEVER fire

A tree where every node is blocked would cycle through them forever.

ROOT CAUSE: `evaluateRound` compares the node's status against
`record.nodeStatusAtStart`, and that field was read AFTER `applySelection` had
already moved pending/blocked to `testing`. So the baseline was always "testing",
`!isResolved("testing")` was always true, and re-blocking an already-blocked node
looked like a fresh verdict.

`tickLoop` now captures the status BEFORE the selection and records that. The
baseline is also more honest on its own terms: it is what the node WAS when the
round started, not what the selection turned it into.

  pending -> blocked   progress (first time)
  blocked -> blocked   NOT progress, so the plateau can fire
  blocked -> rejected  progress
  blocked -> blocked + new evidence  still progress, via evidenceAdded

4 new tests, including one that blocks every node up front and asserts the loop
stops within a handful of rounds instead of spinning.

619 tests, 0 failures.
