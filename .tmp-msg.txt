fix: "no audit loop in this project" was a lie about a read failure

The operator's report: a /loopsec run at round 30, `/loopsec pause 1`, and

    REJECTED: no audit loop in this project

The loop was there. TWO things were wrong and both are now fixed.

1. THE COMMAND LIED ABOUT A READ FAILURE.

`load()` returns an EMPTY snapshot when the read throws. The loop-control verbs —
pause, pause-after-rounds, resume, stop — used `load(cwd).snapshot` directly and never
checked `readError`, so a transient read failure came out as "no audit loop in this
project": the one message that makes an operator believe their audit has been deleted.
`tree`, `log`, `report` and `status` all checked it (39 call sites in that file); these
four did not.

They now go through a `loadOrReport` helper that reports the actual error, says the loop
is NOT gone, and names the file — and changes nothing.

This also explains why the run LOOKED alive: `agent_settled` reads through the same
`load()`, so it was returning early on the empty snapshot while the widget still showed
the last state it had drawn.

2. THE MESSAGE COULD NOT SAY WHICH "NO LOOP".

Three different situations produced one sentence:

    the command was run from a DIFFERENT directory than the audit
    the log is here but records no loop
    the log could not be read

`noLoopErrors(projectRoot)` now distinguishes the first two by checking whether the log
exists, and names the path in both:

    no audit loop here — there is no log at C:\...\.pi-hypothesis\tree.jsonl at all.
    Run this from the directory the audit was started in, or start one here with /loopsec start.

    no audit loop in C:\... — the log exists at C:\...\tree.jsonl but records no loop.
    Start one with /loopsec start.

VERIFICATION

Three tests, and the read-error one is real rather than simulated: `tree.jsonl` as a
DIRECTORY makes `readFileSync` throw EISDIR, so the failure is an actual read failure
and not a stub. A fourth test is a source-level check that the four verbs no longer read
the snapshot without checking `readError` — the failure is an OMISSION, so there is no
output to assert on when the code silently swallows it.

825 tests, 0 failures, tsc clean.
