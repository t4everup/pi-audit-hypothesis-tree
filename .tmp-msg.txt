fix: "no gates recorded" was being reported as "no gates needed"

Reported with a real scenario: an SSRF where the server fetches a caller-directed
URL (file:// included, exfiltrated indirectly through the parsed result), and
"whether there is an echo channel" was NOT assessed.

`chainState` returned `standalone` whenever `requires` was empty:

  const gates = node.requires ?? [];
  if (gates.length === 0) return { state: "standalone" };
  ...
  const chainReady = chains.filter(c => c.state === "standalone" || c.state === "chain-ready");

So a finding whose exploitability was NEVER EXAMINED counted as USABLE, and the
report rendered no chain block for it at all. On the real Centreon tree that
would have read "13/13 可实际利用" for thirteen static, unreproduced claims whose
preconditions nobody had looked at.

That is the same error the impact section already refuses to make — "not
assessed" is not "no impact" — and it is exactly the mechanism that made a
forgotten SSRF precondition SILENT instead of visible.

- `requires: undefined` now means NOBODY ASKED, and `requires: []` means the gates
  were assessed and there are none. The store preserves that difference instead of
  collapsing both to "no gates".
- Two new chain states:
    unassessed  no gates, no preconditions — nobody asked
    untracked   preconditions RECORDED and not one became a hypothesis
- Report wording for both, including what to ask ("入口是否可达？是否需要认证？
  协议/重定向/主机名是否被限制？响应是否回显？").
- The summary counts usability honestly and gains a `利用前提未评估` row:
    | **可实际利用（攻击链完整）** | **0/1** |
    | **利用前提未评估** | 1/1 |
  and a warning that "no preconditions recorded" is not "no preconditions needed".
- `isUsable(state)` replaces the inline check, so "usable" has one definition.

4 new tests, including the SSRF shape: preconditions recorded as prose and never
turned into gates now report as untracked and are NOT counted as usable.

646 tests, 0 failures.
