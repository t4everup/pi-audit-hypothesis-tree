feat: code fences open with a language tag — `c` by default

A fence with no tag gets NO highlighting in any viewer, and the targets this was built
for are mostly C. So `fenceLanguage` is a setting, default `"c"`, and every content
fence in both reports opens with it:

    **调用链**

    ```c
    1. src/http/router.c:88
       router 表把 /diag/ping 标为公开
    2. src/http/ping.c:22
       handle_ping 把 query 的 host 原样传给 run_cmd
    3. src/util/shell.c:41
       system(cmd)
    ```

WHAT IT COVERS

The CONTENT fences: the artifact, the PoC and the call chain, in both the hypothesis
report and the sec report. NOT the static status fence (`认证前可达`), which is a status
line rather than code.

The tag goes on the OPENING fence only — a tagged closer is content, not a closer, and a
report that tags both would render the rest of the document as a code block.

    /hypothesis config fenceLanguage=sh      # or cpp, java, xml, python…
    /hypothesis config fenceLanguage=        # empty turns the tag off

ONE SETTING, NOT ONE PER FENCE, because a report whose evidence block is tagged and whose
PoC block is not looks like a bug. And a tag is a HINT to the viewer, never a claim about
the file: the evidence may be Java, XML or a shell transcript, and tagging it `c` costs
nothing but the wrong colour on a few tokens — a much smaller problem than no highlighting
at all.

`fenceLanguageOf` joins `reportLanguageOf` in settings.ts, read per call for the same
reason: a setting changed mid-run must take effect. The parser accepts only a token
(`[A-Za-z0-9+#.-]*`), because free text would end up on the fence line and break the
block.
