feat: exploitation chains — a sink is not an exploit

Reported: "the assumption holds and it found a command-execution bug, but the bug
needs to combine with something else. The model should hypothesise that
precondition too; if that assumption holds, the whole chain is verified."

THE SCENARIO, verbatim: ScheduledTask.a(byte[]) calls
new ObjectInputStream(...).readObject() with no ObjectInputFilter, and the bytes
come from three BYTEA columns of Scheduled_Tasks. The sink is CONFIRMED — the code
says so. What is NOT confirmed is whether anything can write those columns before
authentication. If it can, it is a pre-auth RCE.

The system could not express that at all:

- `preconditions` is PROSE. Recorded, printed in the report, and never tested by
  anything. Its every use is display or parsing.
- `spawnedFrom` records LINEAGE and deliberately not the relationship — the code
  says so in a comment.
- `hypothesis_combine` REFUSES unconfirmed sources, with a good reason: "a
  combination of unconfirmed hypotheses is speculation stacked on speculation".

That reason is right for a COMBINATION and wrong for the shape above. There are
two different things:

  combination          A and B together give C   -> needs A AND B confirmed
  conditional finding  A gives C IF B holds      -> A confirmed, B is the question

Only the first was modelled, and the second is the commoner shape in real
exploitation. So a confirmed sink was presented exactly like a working pre-auth
RCE, and nothing ever prompted anyone to test the gate.

- `Hypothesis.requires` — the ids that must be confirmed for this finding to be
  USABLE. Settable on hypothesis_add and on hypothesis_vector.
- `ChainState = standalone | gated | chain-ready | broken`, DERIVED from the
  gates' own statuses. A model that could mark its own chain ready would mark
  every chain ready. `broken` (a gate was REFUTED) is checked FIRST: one broken
  link cannot come good, and calling it "gated" would imply it might.
- `hypothesis_record` now NUDGES at the moment the model still has the finding in
  hand: confirmed + preconditions + no gates prints "UNTRACKED PRECONDITIONS ...
  nothing will ever test these ... the report presents this as USABLE, and it may
  not be", with the two commands that fix it.
- SCHEDULED, not left to be noticed: a gate of a confirmed finding gets a
  `gateBoost` of 14, above novelty (10), because verifying it is what converts a
  sink into an exploit. Scoped to gates of CONFIRMED findings — otherwise a model
  that writes many gated findings steers the whole schedule.
- Report: a chain block per finding with the gates marked ✓ / ✗ / … / ?, a
  summary count of USABLE rather than merely confirmed, and a warning not to
  report a gated entry as a working vulnerability.
- Contract clause `requireExploitable` (default FALSE — you usually find the sink
  before the way in): /loop "..." requireExploitable=1
- Validation refuses a gate that is not in the tree, the scope node, itself, a
  duplicate, or that would create a CYCLE. An untracked precondition is prose that
  never gets tested; a cycle means neither finding could ever be ready; and an
  unanswerable "is this chain ready?" reads as "probably fine".

23 new tests, written around the real Scheduled_Tasks scenario: gated -> chain-ready
when the gate is confirmed, broken when it is refuted, several gates needing all,
cycle/self/scope/duplicate refusal, gateBoost ordering, and the contract clause.
