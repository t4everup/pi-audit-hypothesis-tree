fix: the REPRODUCED tier was inflated, and the report contradicted itself

Found by reading the real Checkmk products rather than by reasoning about them.

TWO REAL DEFECTS, both about the report saying things its own data denies.

1. THE TIER WAS INFLATED.

`verificationTier` returned `reproduced` for ANY `command-output` carrying a
command. Measured on the Checkmk run: 2 of 17 HIGH findings held that tier on the
strength of `ls -l` and `grep -c` — and both findings' own `pocExpected` said in
writing "本轮未执行 / 不声称已复现". So finding 16's header read
"已复现（运行过命令，且可重跑）" while its own PoC section, twenty lines below,
said it does not claim reproduction. The tool cannot tell a reproduction from a
reconnaissance by reading the command, so it was guessing, and guessing upward.

The fix does not guess and does not throw information away. It adds a flag and a
tier:

  reproduced    a command-output carrying a command AND `reproduces: true` —
                the author states the output IS the demonstration.
  command-ran   a command-output carrying a command, but nobody declared it
                demonstrates this claim. NEW. `grep`/`ls`/`sed` land here, and
                so does a real reproduction whose author forgot to mark it.

The flag is exposed on `hypothesis_evidence` and `hypothesis_record`, and
`hypothesis_record` nudges once at the moment of confirmation — the only point
where the model still has the command in hand — and accepts "no".

Under-claiming is the safe direction: the command is still recorded, still
printed, and the report states exactly what is missing.

On the Checkmk data the tier distribution moves from 32 reproduced / 0 other to
0 reproduced / 32 command-ran. That is the honest reading: the flag did not exist
when those were recorded, so nobody declared any of them.

2. THE REPORT CONTRADICTED ITSELF.

`probesOff` was emitted whenever `allowCommandProbes` was off, and it ASSERTED
the counts rather than reading them: it was called with `(reproduced, total)` and
printed "all {reproduced} of {total} confirmed findings are STATIC". With 32
reproduced findings it printed "all 32 of 32 confirmed findings are STATIC" — in a
document whose summary, forty lines above, listed "32 条已复现".

It now says where the tier comes from (the author's declaration, not a tool-run
probe) and quotes the real number from ONE source of truth shared with the
summary, so the two halves cannot disagree.

ALSO FIXED, both found in the same pass:

- The summary rows double-counted blocked nodes: "65 recorded" above rows of
  32 + 2 + 31 + 2 = 67. A reader who adds the column up and gets the wrong answer
  stops trusting the rest of the page. `schedulerOrder` now returns pending and
  testing only, which partitions the tree.

- `#### 衍生假设（追索产出，0 条） _未追索…_` put a sentence of small print on the
  heading line, so it rendered as part of the section TITLE.

A BUG THE NEW TEST CAUGHT, which would have made the whole fix inert:

`store.ts`'s `normalizeEvidence` rebuilds each entry from an explicit ALLOWLIST, so
`reproduces: true` was written to the log and silently dropped on the way back in
— no error anywhere, because the record that lost it still validated. The tier
could never have changed. There is now a round-trip test for the whole class, not
just this field.

VERIFICATION

8 new tests. Validated by reverting the four fixes and confirming exactly the
expected tests fail (6 of them; the derived-heading guard was added afterwards
because the revert showed it was missing). 765 tests, 0 failures, tsc clean.

On the real Checkmk state: the summary now reads 32 + 2 + 30 + 2 = 66 against 66
recorded, the self-contradiction is gone, and the derived-hypotheses heading is
clean. Nothing under `E:/aa_qax/a_Audit/` was modified — the report was rendered
in memory only.
